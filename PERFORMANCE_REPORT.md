# Отчёт по производительности QA START

## Актуальность 0.5.0 — 2026-10-09

В reconciliation изменялись только migration filenames/archive, test references, docs и production migration-ledger metadata; runtime application code и production schema/data не менялись. Поэтому повторный безопасный production smoke выполнен, но это не новая замерная кампания производительности.

Последние сопоставимые локальные bounded результаты остаются: 500 GET, concurrency 20, 0 ошибок, около 251 req/s; основные маршруты p95 около 101–103 ms. Это только локальный SSR без авторизованной сессии, не нагрузочный прогноз для PROD. Production нагрузка не выполнялась. Нужны отдельные наблюдения signed-in dashboard/lesson/admin loaders и БД по безопасной staging среде; Docker отсутствие не препятствует текущему релизу, но такой staging сейчас не подключён.

Дата повторных замеров: 2026-10-09. Среда: локальный production build, `vite preview` на `127.0.0.1`; production-сайт не нагружался.

## Production smoke после выкладки 0.5.0

После фактического деплоя выполнены только одиночные read-only HTTP-проверки: `/` — около 48 ms, `/admin/login` — около 16 ms. Это время ответа маршрута в конкретном smoke-запросе, не p95 и не полноценный пользовательский TTFB; сравнивать эти значения с локальными конкурентными прогонами ниже нельзя. Опасная нагрузка по production не проводилась. Кабинет/урок с авторизованной сессией, Archie AI и production DB query timings отдельно не профилировались. Поэтому производительность под наплывом студентов не подтверждена.

## Изменения

- Импорт тяжёлой иллюстрации guide переведён на WebP в `src/components/lesson-guide.tsx` и `src/routes/admin.lessons.tsx`; исходный PNG сохранён, в production bundle не попадает.
- Остальные тяжёлые ресурсы требуют отдельной проверки: `sql-wasm` ~658 kB (326 kB gzip), hero illustration ~254 kB, admin lessons route chunk ~195 kB. Не менялись без профиля фактической загрузки и визуальной проверки.
- Крупные страницы уже представлены отдельными route chunks. Повторные запросы, server timing и Core Web Vitals для авторизованных потоков не удалось достоверно замерить без staging.

## Вывод и следующие шаги

Оптимизация одного крупного изображения дала измеримое сокращение его transfer size на ~1.11 MB. HTML p95 и throughput после неё близки к предыдущему прогону; нельзя приписывать их разницу только WebP, так как HTML не содержит сам файл. Следующий безопасный шаг — staging с обезличенными данными, trace для student/admin сценариев и отдельные DB/API p50/p95; затем принимать решения по wasm lazy-load и агрегирующим запросам аналитики. Production нагрузочное тестирование не выполнялось.
